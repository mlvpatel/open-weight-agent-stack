Orientation

How to read this manual

The views are organised as five concentric rings. A prompt sits inside a context, which runs in a harness, which is judged by evals, which are driven by a loop. Each ring wraps the one before it, and a failure in an inner ring cannot be repaired by an outer one. No amount of eval rigour rescues a prompt that never had an output contract.

What can you actually run?

Everything after this is the same architecture regardless of your hardware. What changes is which models you can serve locally, which runtime you use, and where the ceiling sits. Find your row, then read on normally.

The sizing rule that answers most questions: at 4-bit, weights ≈ parameters × 0.5-0.6 GB, where the quant format decides the exact point in the band. A 7B lands near 4 GB, a 32B near 16-18 GB, a 70B near 35-40 GB. KV cache then grows with context, a 7B is ~5 GB at 4K and 8-9 GB at 32K.

Design method

HLD, LLD, and the rules

This manual doubles as a worked example of design discipline. High-level design fixes components, responsibilities, data flows and trust boundaries, enough to review scope, cost and risk before anyone writes code. Work in order: PRD, then context and container diagrams, then the threat model, then sequence and state diagrams, then API contracts and schemas, then one ADR per hard-to-reverse decision. When a pull request contradicts a diagram, one of them is wrong: fix the diagram in the same PR or reject the change. Draw them in whatever your team opens: Mermaid in the repository (they diff and review like code), Excalidraw or diagrams.net for sketches, Lucidchart or Miro where collaboration already lives.
Harness ring

Master architecture

The request path, top to bottom. Solid arrows carry the request; dotted arrows are state, telemetry and the feedback loop. Cross-cutting layers attach at a single point each so the spine stays readable, memory to the left, observability to the right.

Harness ring

Request lifecycle

One user turn end to end, including the semantic-cache short circuit that skips the model entirely and the tool loop that runs until the goal is met or the step budget is spent.

Four interface patterns follow from this lifecycle, and retrofitting any of them is painful: stream tokens as they arrive; show tool calls as visible steps rather than silence; render citations as links to their sources; and design the retraction path up front, a failed final check replaces the shown answer with a corrected one and says so.

Loop ring

Agent control loop

The state machine the orchestrator actually runs. Every terminal path is explicit, so the agent cannot spin forever.

Why this mattersConflating a network blip with a failed quality gate either hides real failures behind retries or escalates noise to a human. They need separate budgets.
Context ring

RAG pipeline internals

Ingestion runs offline as a batch; query runs per request. Hybrid retrieval fused across dense and keyword search, then reranked by a cross-encoder, is the single highest-leverage upgrade over naive top-k cosine similarity.

Loop ring

Model routing

Sending every request to the largest model is the most common cost and latency mistake. Route by the shape of the task, and escalate only on a failed check.

A self-check is not a gateA model grading its own output is the same failure mode that produced the error, asked politely to notice itself. Keep the verifier on a separate prompt at minimum, and on a separate model when the stakes justify it.
Prompt ring

Prompt and turn contract

The innermost ring, and the easiest to overlook. Everything the outer layers coordinate reduces to one well-specified turn. Order matters: hard constraints first, evidence in the middle, task and output schema last, because instructions at the head and tail survive a long context better than anything buried in the middle.

Two properties make groundedness structural rather than hoped-for. Claims may only cite ids the window actually supplied, and the policy is restated after the untrusted content, so the last thing the model reads is your contract, not an attacker's payload.

Where the named techniques liveFew-shot examples belong in the tool contract and the eval dataset. Chain-of-thought is the thinking budget set per complexity tier. ReAct is the agent loop itself, reflection is the critic, and structured outputs are the JSON schemas the harness validates at the boundary. A technique that exists only as prompt text drifts, one with an owner and a test survives.
Harness ring

Trust boundaries

Four things enter the window and none are trustworthy. The one most teams miss is the third: tool and MCP results feel safe because we made the call, but a GitHub issue body, a Slack message or a scraped page is attacker-controllable text heading straight into context.

The isolation ladderTool execution runs in a container at minimum. When tools run model-written code, climb: gVisor intercepts syscalls below the container, Firecracker gives each execution its own microVM, and hosted sandboxes (E2B, Modal) sell the same isolation as an API when you would rather not operate it yourself.
Context ring

Memory and data tiers

Four tiers with four different lifetimes. Conflating them is what makes an agent forgetful and expensive at the same time, re-reading what it should have summarised, re-deriving what it should have cached.

One boundary before the tiers: your transactional system of record, Postgres, MySQL, the ERP, stays outside the agent entirely. The agent reaches it through tools; memory never becomes a second copy of it.

Reads deserve the same rigour as writesScore memory retrieval by relevance times recency times importance, take the top few, and label them in context as memory rather than fact. On conflict, source-of-truth data beats memory, and newer beats older unless pinned. Every tier gets a TTL; PII is redacted at write time, not read time. Because stored text re-enters future windows, every write gate here is also the memory-poisoning control (ASI06 in section 19).
Eval ring

Guardrails, evals and the improvement loop

Guards run inline on every request and cost milliseconds. Evals run offline against a fixed dataset and gate the release. Production traces feed new cases back into that dataset, the step that actually closes the loop.

Evals do not replace testsThe agent test pyramid, cheapest at the bottom: unit tests with the model mocked, contract tests against every tool's JSON Schema, replay integration tests from recorded responses, eval suites on the golden dataset, simulation with a persona model playing the user, red-team suites mapped to the ASI risks, and chaos drills that kill servers and corrupt tool responses. Determinism rules: temperature 0 and pinned seeds for exact assertions; judged metrics take the median of three runs.

Deployment topology

Three shapes, chosen by how much concurrency you need rather than by what they cost.

Tier A

Single GPU · 24-48 GB

  • RTX 5090 or L40S class
  • 7B-32B at FP8 or AWQ
  • Batch 8-32, interactive latency
One team, sub-second first token
Tier B

Single node · 4-8 GPUs

  • H100/H200 with NVLink
  • 70B-120B via tensor parallelism
  • Continuous batching
Hundreds of concurrent turns
Tier C

Multi-node

  • Tensor parallel in-node, pipeline across
  • Large MoE, high total, few active
  • Separate prefill and decode pools
Opposite bottlenecks, so split them
The sizing rule that decides the shapeWeights plus KV cache plus activations, and KV cache grows with batch size times context length, so it is usually what runs out first, not the weights. A 70B model at 4-bit is 35-40 GB before any KV cache at all. Note also that prefill is compute-bound while decode is memory-bandwidth-bound: batching them into one pool makes both worse, which is why large deployments split them.
Four decisions beyond the box countAvailability: two replicas behind a load balancer once real users depend on it. Rollout: blue-green for model servers (weights preload on the idle colour, traffic flips atomically), rolling for stateless gateway code. Placement: GPUs live where the data lives; cross-region hops cost tens of milliseconds and residency rules may forbid them. Scaling: autoscale on queue depth and KV-cache pressure, never CPU. Multi-node vLLM coordinates workers over Ray. Kubernetes earns its complexity at multi-node scale; below that, docker compose deploys the whole stack.
Context ring

Data lifecycle, deletion and re-indexing

Every store below the source of truth is a derived copy, and each needs its own delete path. This is the gap that turns a right-to-erasure request into an incident: the document leaves the corpus, and its content survives in the vector index, the extracted memory, the answer cache, the traces and the eval set.

The second half is the migration nobody plans for. Changing the embedding model invalidates every vector you hold, the new model's space is not comparable with the old one, so there is no partial upgrade. Build beside, compare, cut over, keep the old index until recall holds.

Freshness is a schedule, not an aspirationRe-ingest changed sources with whatever orchestrator you already run, Airflow, Prefect, Dagster or plain cron, and stamp every chunk with its ingestion time so retrieval can filter or prefer by recency.
Context ring

Databases and state

One system of record, many derived stores. Postgres is the default spine: relational state, pgvector for embeddings, row-level security for tenant isolation, one backup path covering all of it. Everything else earns its place by a workload the spine handles badly, and every derived store stays rebuildable from the source of truth (section 15).

Loop ring

Serving, budgets and rollback

Three operational controls the architecture needs before it meets more than one user. Admission control: one model server and many callers is a queue whether or not you designed one. Budgets: a token cap per user and per tenant, or one runaway agent loop consumes everyone else's capacity. Rollback: the eval gate decides what ships, but nothing else decided what happens when a shipped change goes wrong in production.

Operate to written targetsSet SLOs on the numbers users feel, time to first token, tokens per second, availability, and alert on error-budget burn rate; a dashboard on the cause pages no one. Prometheus scrapes the numbers, Alertmanager routes the page, Grafana sits on top. Keep a one-page runbook for the four failures behind most pages: model-server OOM (restart with a smaller max batch), KV-cache exhaustion (shed long-context requests first), a provider 429 storm (route to the fallback and stop retrying), and a looping agent (the step budget kills it, the alert tells you it fired). Write RTO and RPO down before the incident: Postgres restore drills bound recovery time, and everything else in this stack rebuilds from config.
The error contract is part of the APIMap upstream failures to a small typed set (rate_limited, overloaded, timeout, invalid_output, tool_failed). Every hop gets a timeout smaller than its caller's. Retry only idempotent calls, with exponential backoff plus jitter, capped by the turn budget; a circuit breaker per provider stops retry storms, and the fallback chain rides behind it. Tool calls that write carry idempotency keys so a retry cannot double-post. The user sees one honest sentence and a retry control; the trace carries the detail.
Harness ring

Identity, delegation and authority

Identity is easy to skip and expensive to retrofit, and everything else here depends on it.

The retrieval filter, the cache key and the tool allow-list all enforce an entitlement scope. They are enforcement points; this layer is the decision point that issues the scope they check.

The rule that makes this layer work is attenuation: authority shrinks at every delegation. An agent must never hold more than the user who asked, and a tool call never more than the agent.

The mechanics, named: OIDC / OAuth2 for humans (Keycloak, Auth0, your IdP), SPIFFE/SPIRE for workloads, OPA or Cedar as the policy decision point. Authority travels as short-lived JWTs whose aud, exp and scope claims are checked at every enforcement point; attenuation is OAuth 2.0 token exchange (RFC 8693), a broad token traded for a narrower one, never the reverse; services speak mTLS; and passwords belong to your identity provider, never store or hash user credentials yourself when an IdP can hold them.

Durable memory is an input, not a by-productPrompt injection lasts one turn; a poisoned memory lasts until deleted. Anything promoted from conversation into long-term storage passes the same bar as retrieved content: it carries provenance, it needs corroboration, and an unverifiable claim waits in quarantine rather than becoming permanent.
The tool layer is a supply chainEvery MCP server is a dependency with full access to whatever it is wired to, and latest means someone else decides what your agent can do tomorrow. Pin versions and digests, review declared scopes at install, and treat a server update exactly like a code change.
Cryptography is used here, never inventedTLS for everything in transit, mTLS between services; encryption at rest through each store's native support; SHA-256 digests wherever an artifact is pinned or deduplicated, supply-chain pins, cache keys, idempotency keys; HMAC signatures on every webhook you accept. The rule that outranks any algorithm list: use vetted libraries and platform primitives, implementing cryptographic algorithms yourself is how stacks acquire vulnerabilities, not security.
Secrets follow the same disciplineThey live in a secrets manager, HashiCorp Vault, AWS Secrets Manager, GCP Secret Manager, or SOPS-encrypted files in git for small stacks, reach processes as environment injected at start, rotate on a schedule, and never appear in prompts, traces or model context. A credential the model can read is a credential the transcript now stores.
Performance

Latency budget

Indicative ranges for a 7-32B model on one modern GPU, measure your own, but the shape holds: retrieval and guards are noise, generation is everything.

The number that matters for an agent is not the turn, it is the turn multiplied by the loop. A plan-act-observe cycle running eight model calls pays the prefill cost eight times, which is why prefix reuse outranks almost every other optimisation available.

Separate the two measurements or you will optimise the wrong oneTime to first token is prefill, compute-bound, driven by how much context you pushed in, fixed by pruning and prefix reuse. Time per output token is decode, memory-bandwidth-bound, driven by model size and batch, fixed by quantisation, speculation and a smaller model. A user saying the agent "feels slow" means the first; "takes forever" means the second.
Two levers, spelled outPagedAttention, the idea behind vLLM, allocates KV cache in fixed-size pages the way an operating system allocates virtual memory, so sequences of different lengths pack tightly instead of fragmenting GPU memory; that packing is what makes dense continuous batching possible. Speculative decoding attacks the sequential bottleneck from the other side: a small draft model proposes several tokens, the large model verifies the batch in one forward pass, and the acceptance rule keeps the output distribution identical to the large model alone. It pays most when decode is bandwidth-bound at low batch sizes; measure before adopting.

Model layer

Task-to-model routing

The open-weight frontier moved to trillion-scale MoE: Kimi K3 at 2.8T parameters, Qwen 3.8 Max at 2.4T, DeepSeek V4 Pro at 1.6T. That changes the architecture more than any benchmark does.

"Open-weight" no longer implies "self-hostable." The line that matters now is size, not licence: the frontier open models are consumed through an API exactly like the closed ones. Self-hosting is the mid-tier story, DeepSeek V4 Flash, GLM-4.5-Air, Qwen 3.5 27B, where one node is genuinely enough.

Beyond text, speech and image I/OVoice adds two hops around the same agent: Whisper or faster-whisper transcribes speech in, and an open TTS model speaks the reply out, Piper for CPU speed, Kokoro for quality at 82M parameters. When to fine-tune, the open-weight advantage, used lastThe ladder: prompt first (hours, reversible), retrieve second (days, keeps knowledge current), fine-tune last (weeks, and you own an artifact to version and re-train). Tune for behaviour, format discipline, tone, a repeated mistake, never for knowledge, which belongs in retrieval. LoRA/QLoRA on a 7B-32B covers almost every case: Unsloth for the fastest single-GPU path, Axolotl and LLaMA-Factory config-driven, HF PEFT/TRL underneath, DPO for preferences. vLLM and SGLang serve LoRA adapters at runtime, several on one base model, one deployment, many behaviours.
Pick two, not sevenA fast tier and a frontier tier covers almost everything. Every extra model is another prompt to tune, another eval set to maintain, and another cache that never warms. Add a third only when a measured gap justifies it.

Loop ring

Versioning and change control

A release of an agent system pins five things, and rollback restores the tuple, not one element (section 17): code, prompts and tool contracts, model IDs, index build, and config. When an agent writes code, the PR carries which model, prompt version and step budget produced it, so a bad patch traces back to its configuration and not just its diff.

What gets versioned, where it lives, and the rule that keeps it honest.
WhatWhere it livesRule
CodeGit, trunk-based, short-lived branches, PR reviewThe only write path to production
Prompts and tool contractsThe same repo as code, one file per prompt, changelog per editA prompt edit is a deploy; it rides the same eval gate as code
Model versionsA registry of immutable IDs: MLflow, W&B Artifacts, or a private Hugging Face hubNever "latest" in production; a silent model swap is an unevaluated release
Data and indexesDVC or lakeFS for corpora; each index build stamped with embedder version and chunking configAn index rebuilt with a different embedder is a different index
Eval snapshotsDataset hash plus scores, stored per releaseThe evidence a rollback decision reads
Sequence

Build order and troubleshooting

The layers are not equally urgent. This order keeps the system runnable at every step, which matters more than completeness early on.

  1. UI, orchestrator, model. Layers 2, 3 and 6, a single-node graph and Ollama. You now have a chat app.

  2. The prompt contract. Output schema, citation rule and abstention path, with decoding parameters pinned. An hour of work that every later eval depends on.

  3. Tracing. Layer 11, before anything gets complicated. Debugging an agent without traces is guesswork.

  4. Retrieval. Layer 5, with hybrid search and a reranker from the start. Entitlement filtering goes in on day one if more than one person will use it.

  5. Checkpointing and cache. Layer 9, where latency and cost improve most for the least work.

  6. Tools. Layer 7, one MCP server at a time, each behind schema validation, each result treated as untrusted on the way back in.

  7. Guards, then evals. Layer 10, inline guards first, then a golden dataset before the first prompt change you cannot verify by eye.

  8. Code agent, then hardened serving. Layer 8, and section 22's admission control and rollback, last, once the loop underneath them is trustworthy.

  9. Prefix caching before any hardware upgrade. Agent turns repeat the same system prompt and tool schemas every call; reusing that cache is the cheapest large win available.

  10. Identity before the second user. Section 18: an agent borrowing a human's standing credentials is the most common way a prompt becomes a breach.

  11. Deletion and budgets. Figures 11 and 12. Both are cheap on day one and expensive to retrofit: a per-user token budget before the first shared deployment, and a delete path before the first real user's data enters the index.

Scale the review layers to the stakesA single-team deployment needs neither judge calibration nor a stratified gold set on day one, and adding them early is its own kind of failure. What does not scale down is the trust boundary: the moment untrusted text reaches a tool that can write somewhere, figures 10 and 12 stop being optional regardless of project size.
